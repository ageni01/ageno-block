# I/O 多路复用内核原理：等待队列、epoll 就绪表、LT/ET 与 Reactor

本篇把 API 背后的设计连起来。内核内部名称以 Linux v6.12 源码作为具体阅读坐标；它们不是稳定用户 ABI，后续版本可能调整。以下流程为解释机制的简化模型，不是逐行源码复述。

<!-- more -->

## 1. “等数据”究竟在等什么

socket 接收状态不足时，阻塞 recv 可以把当前线程放进相关等待机制并让出 CPU，条件变化再被唤醒。非阻塞 recv 则不在这里等待，直接 EAGAIN。

内核对象通常提供一种查询就绪状态、登记等待者的接口，Linux 文件操作层可通过 poll 方法和 poll_table 等结构完成协作。这里的“poll 方法”是内核接口概念，不等于应用一定调用了 poll 系统调用。

```text
用户 wait API
   ↓
检查目标对象当前 readiness
   ↓ 若不满足
登记等待关系，进入可被唤醒的等待
   ↓ 数据/关闭/错误发生
目标对象通知等待队列
   ↓
等待线程变成可运行，调度后继续检查/返回结果
```

就绪检查、等待登记、条件重查之间必须有正确同步，避免“刚检查没数据，数据已到却在登记前错过唤醒”的竞态。真实内核用锁、内存序、回调与重查规则协调，不是简单先看一个布尔变量再 sleep。

## 2. select/poll 在内核里大致怎样工作

1. 从用户态读取本次关注的集合/数组。
2. 遍历相关文件，查询其就绪掩码，必要时建立本次等待所需关系。
3. 没有就绪且允许等待，阻塞当前线程；被唤醒后重新检查。
4. 形成返回结果，清理本次等待登记，回用户态。

因此 select/poll 不是“用户不停转圈问内核”，它们可以有效睡眠；主要差别在于每次调用都处理这一组输入和检查对象。poll 的数组比 select 的固定 fd_set 易用，却仍有随集合规模增长的工作。

源码入口可查 [Linux v6.12 fs/select.c](https://github.com/torvalds/linux/blob/v6.12/fs/select.c) 中 do_select、do_poll、poll_initwait 等名字。阅读时分清系统调用包装、集合处理与底层设备/网络对象的 poll 方法。

## 3. epoll 的两个集合

```text
epoll 实例
 ├─ interest：我要长期关注的对象及事件、用户 data
 └─ ready：当前可能有可报告事件的已登记项引用
```

ready 不装应用数据，也不要求每个网络包对应一条 ready 项。一个连接到达十个 TCP 段，不意味着 epoll_wait 必须返回十次；事件可能合并，具体触发与再检查规则决定返回。

### 3.1 ADD 时发生什么

epoll_ctl ADD 找到目标对象，建立 epoll 关注项，记录事件和用户 data；通过目标的 poll 接口登记用于 readiness 变化通知的回调，并检查当前状态。已经就绪的对象在 ADD 时也可以进入后续可报告状态，并不是必须等“下一个包”才触发。

### 3.2 数据到达时发生什么

TCP 接收路径更新 socket 状态并唤醒等待者。epoll 的回调获知相关就绪变化，把关注项挂入 ready 或相应待处理结构，并唤醒等待 epoll 的线程。可能存在多 CPU 并发、回调期间正在转移事件、重复通知等，因此需要锁与额外状态来保证一致性。

### 3.3 wait 时发生什么

epoll_wait 等待 ready 非空，取候选项、按规则重新检查就绪状态，将符合条件的事件复制到用户提供的 events 数组，最多 maxevents 项；LT、ET、ONESHOT 决定后续是否继续可报告、是否需要重新激活。

Linux v6.12 的实现可查 [fs/eventpoll.c](https://github.com/torvalds/linux/blob/v6.12/fs/eventpoll.c) 中 eventpoll、epitem、ep_poll_callback、ep_insert、ep_send_events 等。其关注索引可见红黑树相关结构，就绪管理可见链表等结构。**不要把“用了红黑树”当成 epoll 高效的全部原因**：持久登记和就绪回调减少无差别扫描，才是理解设计的关键。

## 4. epoll 是 O(1) 吗

不能给整个系统一个无条件 O(1)：

- ctl 增删改涉及索引、内存、注册/解除回调和同步，有自己的成本。
- wait 返回 k 个事件，至少要处理与复制这些结果，不能与 k 无关。
- readiness 可能重新检查，活跃对象多时工作仍增加。
- 数据仍要 recv/send，用户仍要解析协议和执行业务。
- 注册关系消耗内核内存，系统还有 fd 和 epoll watch 等资源限制。

合理表述是：epoll 不必在每次 wait 时无条件重扫全部 N 个关注对象，对“大量空闲、少量就绪”的负载通常更有优势。性能还受调度、缓存、锁竞争和业务特征影响。

## 5. LT：条件还成立就继续提醒

LT（level-triggered）是 epoll 默认模式。假定接收队列有 100 字节，只读了 20，还剩 80；下次 wait 仍有机会报告可读。

```text
接收数据：100
wait → IN
recv：20，剩80
wait → IN
recv：80，队列空
wait → 睡眠/等待其他对象
```

LT 更容易写对，但不代表可以不处理部分写、EOF 和背压。可读后一次最多读固定预算、再回循环，是公平性的一种简单做法。

## 6. ET：状态变化通知不能当持续提醒

添加 EPOLLET 开启边沿触发。若只读 20 字节就停，剩余 80 未必再产生你期待的新通知，程序可能一直等待。最实用的规则是：非阻塞 fd，在一次通知中持续读取直到 EAGAIN；监听 socket 持续 accept 到 EAGAIN；写操作持续推进到队列清空或 EAGAIN。

```c
for (;;) {
    ssize_t n = recv(fd, buf, sizeof buf, 0);
    if (n > 0) { append_and_parse(buf, (size_t)n); continue; }
    if (n == 0) { mark_peer_eof(); break; }
    if (errno == EINTR) continue;
    if (errno == EAGAIN || errno == EWOULDBLOCK) break;
    close_connection(); break;
}
```

这是 ET 读处理骨架，辅助函数由应用实现。ET 不能概括成“只通知一次”或“每来一个包通知一次”，也不能通过包数推导回调次数。

### 6.1 ET 与公平性冲突怎么处理

一个热点连接不断来数据，读到 EAGAIN 可能长时间占着线程。生产实现通常结合用户态 ready 队列、每轮字节/操作预算；如果预算耗尽但没读到 EAGAIN，就把连接留在用户态可运行队列，而不是完全依赖下一次内核边沿。

若输入缓冲因业务背压暂时不能继续读，也必须保存“尚未 drain”的状态和恢复策略。不能为了背 ET 口诀而无上限地分配输入内存。

### 6.2 EPOLLONESHOT

一次事件后暂停该项后续通知，处理完通过 MOD 重新激活。适合需要协调多个 worker 不同时操作同一连接的架构，但它不自动解决生命周期、重置时机和线程安全；忘记 rearm 连接会停住。

## 7. 输出状态机为什么必不可少

```text
业务产出响应 → append 到连接 out buffer
  → 立即尝试 send
      全部送入内核 → 清空 buffer，取消 EPOLLOUT
      部分成功/EAGAIN → 保存偏移，关注 EPOLLOUT
  → 下次 OUT → 继续 send
```

输出 buffer 属于应用，发送缓冲属于内核，两者不同。把 1MiB 响应交给一次 send 然后直接丢弃剩余部分，会导致截断。永久关注可写则可能空转。

ET 下，已经有待发数据时通常应立即尝试发送，不是无条件等下一个“变可写”边沿。切换关注时也要遵循相应 API 的再检查规则，避免只按直觉假设所有模式相同。

## 8. 反压：客户端读得慢，服务端怎么办

下游慢 → 本端发送缓冲吃满 → send EAGAIN → 用户 out buffer 累积。如果仍无限 recv 和无限生成响应，用户内存先耗尽。

最简单策略：每连接设置输出高水位，达到时暂停读关注；输出降低后恢复。还可设置低水位避免频繁切换、总内存上限、超时、拒绝策略和业务限流。暂停读取最终会通过接收缓冲与 TCP 窗口反馈影响发送方，但中间还有各层缓冲，不是瞬间停止全链路。

实验中的 LT echo 服务使用固定 64KiB 输出缓冲，满时暂停读，排空后恢复；它演示的是有界状态机，不是生产容量建议。

## 9. Reactor 的组成

```text
连接表：fd/连接ID → 状态对象
事件分发器：select/poll/epoll
读处理器：接收 → 缓冲 → 协议解码
业务处理器：生成结果
写处理器：缓冲 → 部分发送 → 更新关注
生命周期：EOF/错误/超时 → 注销与释放
```

Reactor 的“反应”发生在就绪通知之后，由应用执行 I/O。事件线程只适合做可控、短时工作；慢数据库、长计算或阻塞文件操作会拖住其他连接。使用工作线程池时需要队列、背压以及结果回到连接所属事件线程的唤醒机制，如 eventfd/pipe 等。

一个线程 epoll、一组 worker 并非天然安全：不要多个线程随意 recv 同一个流，否则字节被谁读走和协议解析顺序难以控制。可选择连接归属单线程、任务消息传递，或明确同步与 ONESHOT 的处理模型。

## 10. close 与陈旧事件

close 后 fd 数字可以很快被新连接复用；一次已返回的 events 批次里还可能存着旧的业务标识。直接用数字查表可能误处理新连接。

常见策略是连接 ID + generation 校验、延迟释放状态对象、处理完整批次后再复用槽位。dup/fork 的共享引用会让“close 一个 fd 就必定完全移除关注”的理解失效；epoll 的关注键涉及 fd 和对应打开文件描述。明确 DEL 并集中管理生命周期更容易推理，但 DEL 也不会让用户态已经取回的旧事件数组自动消失。

实验程序把 accept 放在本批旧连接事件处理后，避免同一批内立即复用连接槽；这是简单单线程示例的约束，不是通用并发方案。

## 11. 常见错误清单

| 错误 | 表现 | 正确方向 |
| --- | --- | --- |
| 监听 fd 阻塞，循环 accept | 第一次成功后卡在第二次 | 监听也设非阻塞 |
| ET 只 recv 一次 | 部分数据永久搁置 | drain 到 EAGAIN 或维护用户 ready 状态 |
| 所有连接永久 OUT | 空闲也占满 CPU | 有待发数据才关注 |
| 忽略 send 返回长度 | 响应偶尔截断 | 保留偏移 |
| HUP 就立即丢弃缓冲 | 丢尾部数据/响应 | 读 EOF，按状态排空 |
| recv 后用 strlen | 二进制截断、越界 | 使用实际 n |
| 在事件线程做阻塞业务 | 一个请求拖住全站 | 分离受控任务 |
| 认为 epoll 负责协议拆包 | 无法解释半包 | 每连接独立解析状态 |

## 12. 如何读源码而不迷路

先从一个 API 的问题进入：ADD 怎么登记？socket 到达数据怎么回调？wait 怎么取 ready？再跟文件操作 poll 接口与 socket 等待机制。不要一开始逐行阅读整个 TCP 栈。

固定 v6.12 源码只是为了让名字可定位；用户 API 语义优先参照 [epoll 手册](https://man7.org/linux/man-pages/man7/epoll.7.html)。下一篇：[C 服务端、C++ 客户端与抓包实验](./04-c-cpp-lab.md)。
